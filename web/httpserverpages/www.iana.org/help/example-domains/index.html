IANA-managed Reserved Domains

These domains are reserved by IANA for use in documentation, example code, and testing purposes. They are intentionally not registered to any entity to ensure they remain available for their designated use.

Historical Background

The reservation of example domains dates back to the early days of the Internet when the need for safe, reusable domain names in documentation became apparent. The IETF formalized these reservations to prevent conflicts and ensure documentation clarity.

1999 - RFC 2606
Reserved top-level DNS names for testing and documentation, establishing example.com, example.net, example.org, and test/invalid/localhost TLDs.
2003 - RFC 3172
Defined the .arpa infrastructure domain for reverse DNS resolution and IANA management purposes.
2006 - RFC 4343
Clarified case-insensitive handling of domain names in DNS protocols.
2015 - RFC 7686
Reserved the .onion TLD for Tor hidden services and special-use domain registration.
2020 - RFC 8736
Updated special-use domain considerations and added new reserved entries for internal network use.
2024 - RFC 9461
Further refined the handling of special-use domain names in DNS resolution and validation.

Key Points

Reserved domains will never resolve to actual web servers. DNS resolvers are configured to treat these domains specially. Software developers should use these domains exclusively in documentation, test cases, and configuration examples.

IANA operates under ICANN and is responsible for the global coordination of the DNS Root, IP addressing, and other Internet protocol resources. For more information, visit the IANA website.

Domain Registration Policies

Understanding the domain registration ecosystem helps clarify why reserved domains occupy a special place in the DNS architecture. Domain registration is governed by a multi-layered system of policies, contracts, and technical protocols.

Registration Hierarchy

The domain registration system operates through a hierarchical model. ICANN accredits registrars, who register domains on behalf of registrants under the rules established by each TLD registry. IANA manages the root zone and coordinates the delegation of TLDs to their respective registries.

Reserved Domain Protection

Reserved domains are protected at multiple levels. They are not delegated in the root zone, registrars are contractually prohibited from registering them, and DNS software implementations are expected to handle them as special cases according to RFC 6761.

Technical Specifications

The DNS system operates as a hierarchical distributed database. Understanding its technical foundations helps explain why reserved domains are necessary and how they function within the global Internet infrastructure.

DNS Resolution Process

When a client requests resolution of a reserved domain like example.com, the DNS resolver handles the request according to the special-use domain rules defined in RFC 6761. The key steps include checking local configuration, consulting the root hints, and applying special-use exceptions.

Root Zone Management

The DNS root zone is managed by IANA under contract with ICANN. It contains pointers to all top-level domain registries. Reserved domains are explicitly excluded from delegation in the root zone, ensuring they remain available for their designated purposes.

Best Practices for Developers

When writing documentation, creating test environments, or building applications that reference domain names, following these best practices ensures compatibility and prevents unintended side effects.

In Documentation

Always use example.com, example.net, or example.org when demonstrating URL patterns, API endpoints, or web concepts. This prevents your documentation from accidentally referencing real websites and keeps examples stable over time.

In Test Environments

Use the .test TLD or localhost for local testing. These domains are guaranteed to never resolve to real servers, making them safe for automated testing, CI/CD pipelines, and development environments.

In Configuration Templates

When providing configuration file templates, use example domains as placeholder values. This clearly communicates that the value needs to be replaced while avoiding any real-world conflicts.

In Email Addresses

Use example.com email addresses in sample data, test fixtures, and documentation. Real email addresses should never appear in documentation or public code repositories.

Frequently Asked Questions

Can I register example.com or example.net?

No. These domains are permanently reserved by IANA and are not available for registration through any domain registrar. They are maintained as reserved entries in the DNS root zone.

What happens if someone tries to resolve example.com?

DNS resolvers treat reserved domains specially per RFC 6761. While some resolvers may return NXDOMAIN, others may return a synthesized response. Application developers should not rely on these domains being resolvable.

Are reserved domains available in IDN (Internationalized Domain Name) format?

No. Reserved domain names apply only to their ASCII representations. Internationalized domain names are handled separately through the IDNA protocol (RFC 5890 and related RFCs).

What is the difference between reserved and special-use domains?

Reserved domains (RFC 2606) are set aside for documentation and testing. Special-use domains (RFC 6761) have broader protocol-level significance, such as localhost, which must always resolve to the loopback address 127.0.0.1.

Can I use reserved domains in my application tests?

Yes, absolutely. This is their intended purpose. Using reserved domains in test suites, documentation, examples, and configuration templates ensures you will not accidentally interfere with real domain operations.
