SSL Error Explanation

What is a Hostname Mismatch Error?

A hostname mismatch occurs when the domain name you typed in the browser's address bar does not match the domain name listed in the server's SSL/TLS certificate. The browser checks the certificate's Common Name (CN) field and the Subject Alternative Names (SAN) extension. If the requested hostname is not found in either, the connection is rejected.

This is a critical security check. Without hostname verification, an attacker with a valid certificate for any domain could serve it on a different domain, potentially impersonating a legitimate site. The ERR_CERT_COMMON_NAME_INVALID error prevents this type of attack.

How Hostname Verification Works

Modern TLS implementations follow RFC 6125 for hostname verification. The process involves:

  • Extract the hostname from the request URL
  • Check if it matches any DNS name in the SAN extension (preferred method)
  • Fallback to checking the CN field only if no SAN exists (legacy support)
  • Support wildcard matching (e.g., *.example.com matches sub.example.com)
  • Reject the connection if no match is found

Related Error Types

The following SSL/TLS errors are related to certificate hostname and identity issues:

  • ERR_CERT_COMMON_NAME_INVALID — Certificate hostname does not match the requested domain.
  • ERR_CERT_AUTHORITY_INVALID — Certificate is signed by an untrusted authority.
  • ERR_CERT_DATE_INVALID — Certificate has expired or is not yet valid.
  • ERR_CERT_REVOKED — Certificate has been revoked by the issuing CA.
  • ERR_CERT_CONTAINS_ERRORS — Certificate has structural or encoding errors.
  • ERR_CERT_WEAK_KEY — Certificate uses a key that is too short or weak.
  • ERR_SSL_PINNED_KEY_NOT_IN_CERT_CHAIN — Certificate does not match HPKP pins.
  • ERR_NAME_NOT_RESOLVED — DNS resolution failed for the hostname.
  • ERR_CONNECTION_REFUSED — Server refused the connection entirely.
  • ERR_SSL_PROTOCOL_ERROR — TLS protocol negotiation failed.

Troubleshooting Guide

1. Verify the URL
Check for typos in the URL. A common cause of hostname mismatch is simply typing the wrong domain name. Ensure you are accessing the correct domain.
2. Check Certificate SANs
Use openssl s_client -connect wrong.host.badssl.com:443 | openssl x509 -noout -text to inspect the certificate's Subject Alternative Names. Verify that the domain you are accessing is listed.
3. Check Server Configuration
If you manage the server, ensure each virtual host has the correct SSL certificate assigned. A common misconfiguration is sharing one certificate across multiple domains. Use SNI (Server Name Indication) to serve the correct certificate for each domain.
4. Check Wildcard Certificates
Wildcard certificates only match one level of subdomain. *.example.com matches sub.example.com but not sub.sub.example.com. If you need multi-level subdomain coverage, use a SAN certificate with all required domains.
5. Clear DNS Cache
DNS changes or misconfigurations could route you to the wrong server. Clear your DNS cache with ipconfig /flushdns (Windows) or sudo systemd-resolve --flush-caches (Linux).

Fix Suggestions

For Website Administrators

1
Obtain a Correct Certificate — Request a new certificate that includes all domains and subdomains your server hosts. Use the SAN extension to list all required hostnames. Let's Encrypt supports up to 100 names per certificate.
2
Configure Virtual Hosts Correctly — In Apache, use separate <VirtualHost> blocks with ServerName directives. In Nginx, use separate server blocks. Ensure each block references the correct certificate files.
3
Enable SNI — Server Name Indication (SNI) allows multiple SSL certificates on the same IP address. Ensure your web server has SNI enabled and your clients support it (virtually all modern browsers do).
4
Use a Wildcard Certificate — If you host many subdomains, a wildcard certificate (*.example.com) can simplify management. Note that it only covers one level of subdomains.
5
Test with Multiple Tools — Use SSL Labs (ssllabs.com) and other SSL testing tools to verify your certificate configuration across different clients and scenarios.

For Developers Testing SSL Errors

1
Implement Proper Hostname Verification — Always verify the certificate hostname in your application code. Use built-in TLS libraries that perform this check automatically. Never disable hostname verification.
2
Handle Mismatch Errors Gracefully — Catch hostname mismatch errors and display clear messages to users. Provide actionable guidance, such as checking the URL for typos.

FAQ

Q: What is the difference between CN and SAN?

The Common Name (CN) is a field in the certificate's Subject distinguished name. Subject Alternative Names (SAN) is a separate extension that can list multiple domain names. Modern browsers and RFC 6125 require using SAN for hostname matching. The CN field is deprecated for this purpose in modern certificates.

Q: Can one certificate cover multiple domains?

Yes. Multi-domain (SAN/UCC) certificates can include up to 100 different domain names. Wildcard certificates cover all subdomains at one level (e.g., *.example.com). Combined SAN + wildcard certificates are also available.

Q: Does SNI affect hostname mismatch errors?

SNI tells the server which hostname the client is requesting, allowing it to serve the correct certificate. Without SNI, the server can only serve one certificate per IP address, which may not match the requested hostname. SNI is supported by 99.9% of modern clients.

Q: What is a wildcard certificate?

A wildcard certificate uses an asterisk (*) as a placeholder in the hostname. For example, *.example.com matches www.example.com, mail.example.com, etc. It does not match example.com itself or multi-level subdomains like sub.mail.example.com.

Q: Can IP addresses be used in certificates?

Yes. IP addresses can be listed in the SAN extension using the iPAddress type (not DNS). However, using IP addresses in certificates is uncommon and not recommended for public-facing services. Use domain names instead.

Q: How does this relate to security?

Hostname verification prevents man-in-the-middle attacks where an attacker could use a valid certificate for a different domain to impersonate your target site. Without this check, TLS encryption alone does not guarantee you are communicating with the intended server.
