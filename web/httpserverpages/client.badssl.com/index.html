Client Certificate vs Server Certificate

🔒

Server Certificate

Authenticates the server to the client. Every HTTPS website has one. The browser verifies it automatically.

Direction: Server → Client
Common: All HTTPS sites

👤

Client Certificate

Authenticates the client to the server. Less common. Used for high-security applications.

Direction: Client → Server
Common: Enterprise, APIs, IoT

🔐

Mutual TLS (mTLS)

Both server and client certificates are required. Both parties authenticate each other.

Direction: Bidirectional
Common: Zero-trust, microservices

SSL Error Explanation

What is Client Certificate Authentication?

Client certificate authentication (also known as mutual TLS or mTLS) is a TLS feature where the server requests the client to present a certificate during the handshake. This provides strong, certificate-based authentication that is more secure than passwords or API keys.

When you visit this page without a client certificate, the TLS handshake fails. The browser may display an error like ERR_SSL_CLIENT_AUTH_CERT_NEEDED or prompt you to select a client certificate. If no suitable certificate is available, the connection cannot be established.

How Client Certificate Authentication Works

  • The server sends a CertificateRequest message during the TLS handshake
  • The message lists acceptable Certificate Authorities (CAs)
  • The client selects a certificate issued by one of the accepted CAs
  • The client sends its certificate and proves possession of the private key
  • The server validates the client certificate (chain, expiration, revocation, EKU)
  • If validation succeeds, the handshake completes and the application layer begins

Common Error Codes

  • ERR_SSL_CLIENT_AUTH_CERT_NEEDED (Chrome/Chromium)
  • SSL_ERROR_BAD_CERT_ALERT (Firefox)
  • ERR_BAD_SSL_CLIENT_AUTH_CERT (Chrome - rejected cert)
  • NSURLErrorClientCertificateRequired (iOS/macOS)
  • SSL_ERROR_NO_CERTIFICATE (OpenSSL - client has no cert)
  • SSL_ERROR_CERTIFICATE_UNKNOWN (OpenSSL - server rejected cert)

Authentication Flow

Step 1: Client initiates TLS connection to client.badssl.com
Step 2: Server presents its valid server certificate (standard TLS)
Step 3: Server sends CertificateRequest listing accepted CAs
Step 4: Browser prompts user to select a client certificate
Step 5: If no certificate is available, connection fails with error
Step 6: If certificate is selected, client sends it to the server
Step 7: Server validates the client certificate chain and EKU
Step 8: If valid, server grants access; if invalid, connection is terminated

Related Error Types

The following SSL/TLS errors are related to client certificate authentication:

  • ERR_SSL_CLIENT_AUTH_CERT_NEEDED — Server requires a client certificate but none was provided.
  • ERR_BAD_SSL_CLIENT_AUTH_CERT — The provided client certificate was rejected by the server.
  • SSL_ERROR_BAD_CERT_ALERT — Server rejected the client certificate (Firefox).
  • SSL_ERROR_NO_CERTIFICATE — Client has no certificate to send (OpenSSL).
  • SSL_ERROR_CERTIFICATE_UNKNOWN — Server could not process the client certificate.
  • ERR_CERT_AUTHORITY_INVALID — Client certificate is signed by an untrusted CA.
  • ERR_CERT_DATE_INVALID — Client certificate has expired or is not yet valid.
  • ERR_CERT_REVOKED — Client certificate has been revoked.
  • NSURLErrorClientCertificateRequired — Server requires client certificate (iOS/macOS).
  • ERR_SSL_PROTOCOL_ERROR — TLS protocol negotiation failed during mTLS.

Troubleshooting Guide

1. Install the Client Certificate
If you have a client certificate (.p12/.pfx or .pem), install it in your system's certificate store. On Windows, double-click the .p12 file and import it. On macOS, add it to Keychain Access. On Linux, configure your browser's SSL directory.
2. Check Certificate Format
Client certificates typically come in PKCS#12 (.p12/.pfx) format containing both the certificate and private key. Ensure the file is not corrupted and the password is correct. Convert between formats using OpenSSL: openssl pkcs12 -in cert.p12 -out cert.pem -clcerts
3. Verify the Issuing CA
The client certificate must be issued by a CA that the server accepts. Check the server's CertificateRequest message to see which CAs are accepted. Use openssl s_client -connect client.badssl.com:443 to inspect the accepted CA list.
4. Check Extended Key Usage
The client certificate must have the Client Authentication EKU (OID: 1.3.6.1.5.5.7.3.2). Certificates with only Server Authentication EKU will be rejected. Verify with: openssl x509 -in cert.pem -noout -text | grep "Client Authentication"
5. Check Certificate Validity
Ensure the client certificate has not expired and is within its validity period. Also verify that the issuing CA's certificate chain is intact and trusted.
6. Configure Browser Certificate Selection
In Chrome, navigate to chrome://settings/certificates to manage client certificates. In Firefox, go to Settings → Privacy & Security → View Certificates. Ensure the certificate is in the correct store and marked as usable for client authentication.

Fix Suggestions

For Website Administrators

1
Set Up a Client CA — Create or obtain a CA for issuing client certificates. For internal use, OpenSSL can create a private CA. For production, use a commercial CA or your organization's PKI infrastructure.
2
Configure Server for mTLS — In Nginx, use ssl_client_certificate and ssl_verify_client on. In Apache, use SSLVerifyClient require and SSLCACertificateFile. Specify the CA that signed the client certificates.
3
Issue Client Certificates — Generate client certificates signed by your CA. Each user or device should receive a unique certificate. Include the Client Authentication EKU. Set appropriate validity periods and enforce renewal policies.
4
Implement Certificate Revocation — Set up OCSP stapling or CRL distribution to revoke compromised or expired client certificates. Configure the server to check revocation status during the handshake.
5
Monitor and Audit — Log all client certificate authentication events. Monitor for unusual patterns, such as certificate reuse across devices or authentication from unexpected locations.

For Developers Testing Client Auth

1
Handle Client Auth Errors — Detect when a server requires a client certificate and prompt the user appropriately. Provide clear error messages explaining what a client certificate is and how to obtain one.
2
Implement Certificate Selection UI — When multiple client certificates are available, present a selection interface. Show the certificate subject, issuer, and expiration to help users choose the right one.
3
Test with This Page — Use client.badssl.com to test your application's behavior when encountering a server that requires client certificates. Verify that the correct error handling is in place.

FAQ

Q: What is the difference between client certificates and passwords?

Client certificates provide stronger authentication than passwords. They use public-key cryptography, are resistant to phishing (the browser handles them automatically), and support fine-grained revocation. Unlike passwords, private keys never leave the client device.

Q: Can client certificates be used on mobile devices?

Yes. Both iOS and Android support client certificates. On iOS, install via mobile device management (MDM) profiles. On Android, install via the Security settings or through enterprise management. Some browsers on mobile have limited client certificate UI.

Q: How do I get a client certificate for testing?

You can create your own test client certificate using OpenSSL: generate a private key, create a CSR, sign it with a test CA, and export as PKCS#12. For testing with badssl.com, you would need a certificate signed by their test CA.

Q: What is certificate pinning in the context of client certificates?

Certificate pinning for client certificates means the server expects a specific client certificate (or public key) rather than any certificate from a trusted CA. This provides the strongest authentication but requires careful management of certificate distribution and rotation.

Q: Does mTLS impact performance?

mTLS adds minimal overhead to the TLS handshake (one additional round trip for the client certificate exchange). The cryptographic operations for verifying the client certificate add a small amount of CPU time. For most applications, this overhead is negligible.

Q: How do I revoke a client certificate?

Client certificates can be revoked through OCSP (Online Certificate Status Protocol) or CRL (Certificate Revocation List). The server should check the revocation status during the handshake. For large deployments, short-lived certificates (hours or days) with automated renewal are a modern alternative to revocation.

Q: What is the relationship between client certificates and smart cards?

Smart cards and hardware security tokens (like YubiKey) store client certificate private keys in secure hardware. The private key never leaves the device, providing the highest level of security. The browser communicates with the smart card via PKCS#11 or platform APIs to perform the TLS handshake.
