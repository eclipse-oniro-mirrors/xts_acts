SSL Error Explanation

What is an Untrusted Root Certificate Error?

Every SSL/TLS certificate chain must be anchored to a trusted root certificate authority (CA). Root certificates are pre-installed in your operating system or browser's trust store. When a server presents its certificate, the browser verifies that every certificate in the chain leads back to a trusted root. If the root CA is not in the trust store, the entire chain is considered untrusted.

The error ERR_CERT_AUTHORITY_INVALID (or CERT_AUTHORITY_INVALID) means the certificate chain could not be built to a trusted root. This can happen because the root CA is genuinely untrusted, the intermediate certificates are missing, or the server is misconfigured.

How Certificate Trust Works

The PKI (Public Key Infrastructure) trust model works as follows:

  • Root CAs are self-signed and pre-installed in trust stores by OS vendors and browser makers
  • Root CAs issue certificates to Intermediate CAs, which in turn issue end-entity certificates
  • Browsers validate the chain by checking each signature and verifying the root is trusted
  • If any link in the chain is broken or untrusted, the entire chain fails validation
  • Trust stores are maintained by Microsoft, Apple, Google, and Mozilla with regular updates

Related Error Types

The following SSL/TLS errors are related to certificate trust and chain issues:

  • ERR_CERT_AUTHORITY_INVALID — Certificate signed by an untrusted authority.
  • ERR_CERT_COMMON_NAME_INVALID — Certificate hostname does not match the requested domain.
  • ERR_CERT_DATE_INVALID — Certificate has expired or is not yet valid.
  • ERR_CERT_REVOKED — Certificate has been revoked by the issuing authority.
  • ERR_CERT_CONTAINS_ERRORS — Certificate contains structural or encoding errors.
  • ERR_CERT_WEAK_SIGNATURE_ALGORITHM — Certificate uses a weak or deprecated signature algorithm.
  • ERR_SSL_PINNED_KEY_NOT_IN_CERT_CHAIN — Certificate does not match expected public key pins.
  • ERR_CERT_NO_REVOCATION_MECHANISM — Certificate has no OCSP or CRL endpoint.
  • ERR_CERT_UNABLE_TO_CHECK_REVOCATION — Unable to verify certificate revocation status.
  • ERR_CERT_SELF_SIGNED — Certificate is self-signed and not in the trust store.

Troubleshooting Guide

1. Check for Missing Intermediate Certificates
The most common cause of untrusted root errors is missing intermediate certificates. The server must send the full chain (leaf + intermediates). Use openssl s_client -showcerts to verify all chain certificates are being sent.
2. Verify the CA is Trusted
Check if the CA that issued the certificate is in your trust store. Internal CAs (corporate, development) need to be manually installed. Public CAs should be in the trust store automatically.
3. Install the Root Certificate
For internal or development CAs, install the root certificate in the system trust store. On Windows, use certmgr.msc. On macOS, add to Keychain Access. On Linux, update the ca-certificates package.
4. Check Certificate Order
Ensure certificates are sent in the correct order: leaf first, then intermediate(s). Some servers require explicit configuration of the certificate chain file. Apache uses SSLCertificateChainFile; Nginx concatenates certs in the ssl_certificate file.
5. Cross-Signing Issues
Some CAs use cross-signing where a certificate is signed by multiple roots. If the wrong cross-signed intermediate is sent, the chain may not build to a trusted root. Ensure the server sends the correct cross-signed intermediate.
6. Update Trust Store
Outdated operating systems may have stale trust stores. Update your OS to receive the latest root CA certificates. Windows, macOS, and major Linux distributions push trust store updates regularly.

Fix Suggestions

For Website Administrators

1
Use a Publicly Trusted CA — Obtain a certificate from a publicly trusted CA like Let's Encrypt, DigiCert, GlobalSign, Sectigo, or Cloudflare. These CAs are in the trust stores of all major browsers and operating systems.
2
Include Full Certificate Chain — Configure your server to send the complete certificate chain. For Nginx, concatenate the leaf and intermediate certificates into one file. For Apache, use the SSLCertificateChainFile directive.
3
Test with SSL Tools — Use SSL Labs (ssllabs.com) to test your certificate chain. It will report any missing intermediates or chain issues. Aim for an A rating.
4
Monitor CA Trust Status — Occasionally CAs lose their trusted status due to misissuance or compliance issues. Monitor the CA/Browser Forum and Mozilla's root store policy for changes. Have a plan to switch CAs if needed.
5
For Internal CAs, Distribute the Root — If you must use an internal CA, deploy the root certificate to all clients via group policy (Windows), MDM (macOS/iOS), or configuration management tools (Linux).

For Developers Testing SSL Errors

1
Implement Proper Trust Validation — Use the platform's built-in TLS libraries which handle trust validation automatically. Never implement custom certificate validation unless absolutely necessary.
2
Test with Various Trust Scenarios — Use this untrusted root test page and other badssl.com test domains to verify your application handles different trust failure scenarios correctly.
3
Support Custom Trust Anchors — If your app needs to support custom CAs, provide a secure mechanism for users to install additional trust anchors. Never silently accept all certificates.

FAQ

Q: What is a trust store?

A trust store is a collection of pre-installed root CA certificates that your operating system or browser uses to validate SSL/TLS certificate chains. Different platforms maintain their own trust stores: Microsoft (Windows), Apple (macOS/iOS), Google (Android/Chrome), and Mozilla (Firefox).

Q: How do root CAs get into the trust store?

Root CAs must pass rigorous audits and comply with CA/Browser Forum guidelines. Browser and OS vendors evaluate CA applications and add approved roots to their trust stores. Roots can also be removed if they violate trust requirements.

Q: What is a self-signed certificate?

A self-signed certificate is one where the issuer and subject are the same entity. Self-signed certificates are not inherently trusted because there is no third-party CA to vouch for the identity of the certificate holder. They are commonly used in development and internal networks.

Q: Can I add my own root CA to the trust store?

Yes. You can manually install root certificates in the system trust store. This is common for corporate environments with internal CAs. However, this must be done on every client device, and users must trust the entity managing the CA.

Q: What happens when a CA is distrusted?

When a root CA is removed from trust stores (e.g., DigiNotar in 2011), all certificates issued by that CA become invalid. Websites must obtain new certificates from a different CA. This can cause widespread outages if not planned for.

Q: What is certificate transparency (CT)?

Certificate Transparency is a system that publicly logs all issued SSL certificates. This allows domain owners to monitor for unauthorized certificates and helps browsers detect misissued certificates. Google Chrome requires CT log entries for all publicly trusted certificates.
